## 2. 미이행 — P0 계열 잔여

### 2-1. 변환 작업의 강제 중단 불가 (P0-3 핵심)

**현재**: 변환 타임아웃(30초)은 대기만 중단하고 스레드는 계속 돈다. 악의적 PDF/HWPX가
CPU를 계속 점유할 수 있다. 동시 변환은 2개로 제한했고 요청 자체도 8개로 막았으므로
피해 규모는 제한되지만, **근본적으로 중단은 불가능하다.**

**필요한 것**: 변환을 별도 프로세스(`ProcessPoolExecutor` 또는 서브프로세스)로 격리하고
CPU·메모리·시간 rlimit를 걸어 강제 종료. 규모가 크고 배포 형태(단일 컨테이너)에 영향을 준다.

**임시 완화**: `PLW_CONVERT_CONCURRENCY`를 낮추고 `PLW_MAX_FILE_BYTES`를 줄이면 노출이 준다.

### 2-2. ZIP·PDF 세부 한계 미적용 (P0-3)

압축 해제 총량(50MB)만 제한하고 **항목 수·개별 항목 크기·압축비·PDF 페이지 수**는 제한이 없다.
`check_zip_safety`가 선언된 `file_size`를 신뢰하는 점도 그대로다(파이썬 zipfile이 초과분을
절단하므로 실질 위험은 낮다고 판단해 보류).

### 2-3. 룰 검사 요청의 속도 제한 없음 (P0-3)

`use_llm=false` 요청에는 쿼터가 없다. 동시 요청 8개 제한이 유일한 방어이며,
**IP별 분당 요청 수 제한이 없다.** 비용은 들지 않지만 CPU 소모는 가능하다.

### 2-4. 관리자 인증 방식 (P0-4) — 전면 미이행

`/?admin=<토큰>` + `localStorage` 구조가 그대로다. 판단:

- 실질 위험은 **최초 요청 URL이 Fly 접근 로그에 남는 것** 하나 (주소창은 `history.replaceState`로 즉시 제거)
- 동일 출처 XSS로 토큰 유출 가능하나, XSS 경로는 이전 리뷰에서 검증됨
- HttpOnly 세션 쿠키로 바꾸려면 별도 로그인 화면·세션 저장소가 필요 — 1인 운영 도구에 과할 수 있음

**권장**: ① 현재 토큰 회전 ② Fly 로그에서 과거 토큰 노출 여부 확인.
그 다음에 세션 방식 전환 여부를 결정.

**해결됨(2026-08-01)**: 관리자 일일 상한 `PLW_ADMIN_DAILY`(기본 100) 추가.
공개 전역 캡과 분리된 축이라 관리자 사용이 일반 쿼터를 잠식하지 않는다.
토큰도 회전했고 `PLW_QUOTA_SALT`를 고엔트로피 값으로 설정했다.
**남은 것**: 인증 방식 자체(URL 토큰 + localStorage)는 그대로다 — 위 판단 참조.

## 3. 미이행 — P1 계열 잔여

### 3-1. 의존성 재현성 (P1-2) — 부분 이행(2026-08-01)

**이행**: 엔진을 커밋 SHA(`cd94b77`)로 고정. 컨테이너 non-root(uid 10001) 전환 —
Fly 볼륨이 root:root로 마운트되므로 엔트리포인트가 DB 디렉터리 소유권만 넘기고
`setpriv`로 권한을 내려놓는다. 배포 후 쿼터 쓰기(100→99)로 실제 동작 확인.

**주의**: 엔진을 고칠 때마다 `requirements.txt`의 SHA를 갱신하고 하네스를 재실행해야 한다.

**미이행**: 전이 의존성 lock·hash 검증, CI의 취약점·시크릿 스캔·SBOM,
Docker base 이미지 digest 고정.

### 3-2. 프록시 헤더 신뢰 기본값 (P1-4) — 부분

`PLW_TRUST_PROXY_HEADERS` 기본값이 여전히 `1`(신뢰)이다. Fly 배포에서는 올바르나,
**Fly 밖(로컬 `docker run` 등)에서는 임의 `X-Forwarded-For`로 IP 쿼터를 우회할 수 있다.**
기본값을 비신뢰로 뒤집으면 Fly 배포에서 모든 사용자가 같은 IP로 묶여 쿼터가 공유되는
회귀가 생기므로, "Fly 프록시 검증 후 사용" 로직이 함께 필요하다.

### 3-3. 쿼터 솔트 (P1-1) — 해결됨(2026-08-01)

`PLW_QUOTA_SALT`를 고엔트로피 값(48자)으로 Fly 시크릿에 등록했다.
코드의 기본값은 로컬 개발·테스트용으로만 남는다.
**남은 것**: 운영에서 미설정 시 기본값으로 조용히 동작한다 — 시작 시 경고 로그를 남기면 더 안전하다.

## 4-1. 실파일 검증 (원래 계획의 Step 8) — 완료(2026-08-01)

실제 한글 파일 8건으로 검증했다. 그전까지 hwpx 테스트는 전부 합성 XML이었다.

- `.hwpx` 6건 전부 변환 성공 — 표 행 조인·제목 승격이 실파일에서 동작
- 실제 예비창업패키지 사업계획서 PDF: 8,169자 변환 + PSST 4개 섹션 전부 인식, 오탐 0

**발견·수정**: PSST 서식이 아닌 문서는 섹션 매칭이 0이 되어 '필수 항목 누락' 치명 4건이
쏟아졌다. 성립하는 사실은 '이 서식이 아니다' 하나뿐이므로 info 안내 1건으로 통합했다
(일부라도 매칭되면 나머지 누락은 진짜 결함이므로 유지). 실측: 치명 4 → 안내 1.

**남은 것**: 프로파일 선택 UI가 없어 psst-standard 고정이다. 다른 공고 서식을 제대로
검사하려면 프로파일 추가 + 선택 UI가 필요하다(v1에서 v2로 미룬 항목).

## 5. 이번 작업에서 새로 발견한 것

### 5-1. LLM 호출 수가 문서 헤딩 수에 비례 (리뷰 문서보다 심각)

리뷰 문서는 "최대 12회"로 봤으나, 엔진의 per-section 체커는 **프로파일 4섹션이 아니라
문서의 모든 헤딩 섹션**을 순회한다. 소제목 20개 문서 실측 **42회**.
헤딩 승격 휴리스틱이 번호 매긴 줄을 제목으로 올리므로 실제 서식에서 쉽게 커진다.

이번에 요청당 상한(24회)으로 막았으나 **근본 해결은 엔진 쪽**이다 —
섹션들을 한 번의 호출로 묶으면 비용이 크게 준다. `plan-lint` 저장소 과제.

### 5-2. 예산 상한과 검사 품질의 트레이드오프

24회 예산은 섹션 검사 2종에 각 10개 섹션까지를 배정한다. 그보다 긴 문서는 뒷부분이
AI 검사에서 빠지고 **어떤 검사가 잘렸는지 이름으로** 고지된다. 품질을 올리려면 예산을
키워야 하고 비용이 비례해 는다. 5-1의 엔진 개선이 이 트레이드오프를 없애는 정석이다.

### 5-3. (해결됨) 예산 독식으로 인한 핵심 검사 미실행

총량만 제한한 최초 구현에서, 섹션 38개 문서는 unsupported-claim이 24회를 전부 소진해
**내부 모순·구체성 부족·보강 제안이 아예 실행되지 않았다.** 체커별 몫 배분(`plan_shares`)으로
해결했고, 회귀 테스트(`test_long_document_still_runs_whole_doc_checks_and_enrich`)로 고정했다.

### 5-4. 비용 추정치 정정

최초 README에 적은 "하루 최대 1.5만~1.7만원"은 과대추정이었다. 6.5만 자 문서 실측 결과
요청당 입력 약 22,500토큰(≈63원), 전역 50건 기준 **하루 최대 약 3,200원**이다.
(예산 상한이 긴 문서의 호출을 잘라내므로 문서가 길어져도 비용이 선형으로 늘지 않는다.)
